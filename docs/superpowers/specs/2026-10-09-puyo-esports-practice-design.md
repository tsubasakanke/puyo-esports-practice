# ぷよぷよeスポーツ 練習用クローン 設計書

作成日: 2026-10-09

## 1. 目的と成功の基準

**目的**: Switch の「ぷよぷよeスポーツ」の感覚のまま、PC のブラウザでひとりでも友達とでも練習できるゲームを作る。

**ユーザーが決めたこと**
- ルールは「通」と「フィーバー」の2つ
- CPU 対戦と、オンラインのマルチ（最大4人）。ローカルの複数人プレイはなし
- 操作は PC のキーボードがメイン
- 前作 Puzzle Battle（`~/puzzle-battle`）の反省を活かす。枠のサイズ・背景・通とフィーバーの見た目の違いがシンプルすぎて別ゲームに見えたので直す。フィーバーのツモの形（3個・4個・でかぷよ）を入れる
- ぷよはツヤとぷにっとした質感を再現する。著作権に触れない範囲で寄せる

**成功の基準**
1. 原作の実測フレーム表（設置・連鎖・ちぎり）と、エンジンの値が自動テストで一致する
2. 同じシードなら、原作と同じ配ぷよが出る（eスポ互換の乱数）
3. 2〜4人のオンライン対戦が、ラグがあっても操作感を落とさずに最後まで遊べる
4. 画面を見て「ぷよぷよeスポーツっぽい」と感じられる。ぷよの質感、枠の比率、通とフィーバーの見た目の違い
5. 60fps を保つ（4人対戦＋エフェクトあり、一般的なノートPC）

**作らないもの**
- SEGA の画像・音楽・キャラクター・ボイス・ロゴの使用。原作ぷよの顔のデザインもまねしない
- スマホのタッチ操作（あとで追加できる作りにはしておく）
- ローカルの複数人プレイ、ゲームパッド（あとで追加できる）
- ストーリーモード、キャラクター選択

## 2. 技術選定

| 役割 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型でルールのバグを減らせる。前作と同じ |
| ビルド | Vite | 前作と同じ。開発サーバーが速い |
| 描画 | PixiJS v8（WebGL） | ツヤ・ぼかし・パーティクルを4盤面ぶん出しても軽い |
| テスト | Vitest | 前作と同じ |
| オンライン | Firebase Realtime Database＋匿名認証 | 前作の Firebase プロジェクト `puzbattle` を使い回す（無料の Spark プラン） |
| 公開 | GitHub Pages（GitHub Actions） | URL を送るだけで友達が遊べる |

リポジトリは `~/puyo-esports-practice`。前作とは別にする。`Transport` インターフェース（Firebase とメモリ実装の差し替え）は前作 `src/net/transport.ts` から移植する。

## 3. 全体の構成

ルール・描画・通信を完全に分ける。エンジンは「入力を受け取って1フレーム進める」だけの決定的な計算にする（同じシード＋同じ入力なら必ず同じ結果）。これでテスト、CPU の先読み、リプレイ、オンラインの相手盤面の再生に同じエンジンを使える。

```
src/
  engine/              ルール本体。描画・通信・DOM を参照しない
    rng.ts             eスポ互換の乱数と配ぷよ生成
    field.ts           盤面（6列×14段）、連結判定、消去、落下
    piece.ts           ツモの形と回転・壁蹴り・床蹴り・クイックターン
    player.ts          1人分の状態機械（フレーム単位）
    garbage.ts         予告・相殺・おじゃま落下の列決定
    score.ts           得点計算
    rules/tsu.ts       通ルールの定数と差分
    rules/fever.ts     フィーバールールの定数と差分（ゲージ、フィーバー盤面、ツモの形）
    match.ts           2〜4人の試合進行、攻撃先、勝敗、先取数
    events.ts          エンジンが出すイベントの型（描画・音・通信が購読する）
  ai/                  CPU。Web Worker で動かす
  render/              PixiJS の描画（ぷよ、エフェクト、レイアウト、背景）
  audio/               効果音（Web Audio で生成）
  net/                 部屋・同期
  input/               キーボード（DAS・ARR 設定つき）
  ui/                  タイトル、モード選択、設定、ロビー、結果
```

**依存の向き**: `ui` → `render`/`net`/`ai`/`input` → `engine`。`engine` はどこにも依存しない。

**時間の扱い**: エンジンは 1/60 秒の固定ステップで動かす。描画はモニターのリフレッシュレートで動かし、前後フレームの間を補間する。タブが裏に回って時間が飛んだときは、追いつくまでまとめて進める（最大 30 フレームまで。それ以上は捨てる）。

**画面の流れ**: タイトル → モード（ひとり練習／CPU 対戦／オンライン）→ ルール（通／フィーバー）→ 対戦 → 結果（先取数の表示つき）→ もう一回 or 戻る。設定画面はタイトルから開く（キー割り当て、DAS・ARR、音量、色のマーク表示）。

## 4. ルールエンジン（通ルール）

数値の出典は §12 の調査メモ。「推測」と書いた値は、原作の公開データがないので旧アーケード版ぷよ通の解析値を使い、実測の設置フレーム表に合うように調整する。どの値も `rules/tsu.ts` の定数にまとめて、変えやすくする。

### 4.1 盤面
- 6列×12段が見える範囲。13段目は置けるが、連結しても消えない。14段目は回転のときだけ入れて、設置後にそこに残ったぷよは消える（14段目の扱いはeスポの情報がないので推測）
- 窒息点は3列目12段目。次のツモを出すときに埋まっていたら負け
- 出現は3列目、軸ぷよが下の縦向き

### 4.2 1人分の状態機械
```
出現 → 操作中 → 設置 → ちぎり落下 → 消去判定 ─┬→ 連鎖（消去 → 落下 → 判定 を繰り返す）
                                                └→ おじゃま落下 → 窒息判定 → 次の出現
```
状態ごとに残りフレーム数を持ち、`step(input)` で1フレームずつ進める。

### 4.3 操作
| 項目 | 値 | 確度 |
|---|---|---|
| 自然落下 | 16F/段 | 推測 |
| ソフトドロップ | 2F/段 | 実測から逆算 |
| 横移動 | 押した瞬間に1マス。長押しは 8F 後から 2F ごと（設定で変えられる） | 推測 |
| 接地から固定まで | 32F。ソフトドロップ中は即固定。床蹴りで持ち上がるのは 8 回目で即固定 | 推測 |
| 回転 | 右回転・左回転。壁蹴り、床蹴りあり | 確定 |
| クイックターン | 左右が両方ふさがっているとき、回転を2回押すと上下が入れ替わる | 確定 |
| 1手目 | 開始前に +7F | 実測 |

### 4.4 連鎖のテンポ
- 1連鎖のフレーム数 = 消去 55F ＋ 落下（落下がなければ 0、あれば 25F ＋ 2F×(最大落下段数 − 1)）。実測の「落下なし 55F／1段 80F／9段 96F」と一致する
- ちぎりの追加フレーム（段差 → F）: 1→19, 2→24, 3→28, 4→31, 5→34, 6→37, 7→40, 8→42, 9→44, 10→46, 11→48

### 4.5 得点
- 1連鎖の得点 = 消した個数 × 10 × clamp(連鎖ボーナス＋連結ボーナス＋色数ボーナス, 1, 999)
- 連鎖ボーナス（1〜19連鎖）: 0, 8, 16, 32, 64, 96, 128, 160, 192, 224, 256, 288, 320, 352, 384, 416, 448, 480, 512
- 連結ボーナス（1グループの個数）: 4→0, 5→2, 6→3, 7→4, 8→5, 9→6, 10→7, 11以上→10
- 色数ボーナス: 1色→0, 2色→3, 3色→6, 4色→12, 5色→24
- 落下ボーナス: ソフトドロップ1段につき1点（推測）。次の連鎖のおじゃま計算に加わる
- 全消し: 次に連鎖したとき、おじゃまを +30 個

### 4.6 おじゃま
- 送る数: (得点 ÷ レート ＋ 前回の端数) の切り捨て。端数は持ち越す。レートの初期値は 70
- 相殺: 自分の予告から先に減らし、余りを相手に送る
- 予告表示: 小=1, 大=6, 岩=30, 星=180, 月=360, 王冠=720, 彗星=1440。大きい単位から並べて最大6個表示
- 1回に降るのは最大 30 個（5段）
- 降る列: 6の倍数ぶんは全列に均等。端数（1〜5個）はランダムに選んだ別々の列に1個ずつ。乱数は試合シードから作った別系列を使う（オンラインでも全員の結果が一致するように）
- 降る速さは列ごとに違う。1段目に着地するまでの F: 1〜6列目 = 60, 59, 64, 56, 62, 58
- 着地後の硬直: 8個以下 0F、9個 1F … 18個 15F、30個 25F（間は実測表から線形補間）
- 降るタイミング: 自分の連鎖が終わって次のツモを出す直前だけ。相手の連鎖が終わる前に設置すれば、予告が確定する前に次のツモを引ける（原作の挙動）

### 4.7 マージンタイム
試合開始から 96 秒で始まり、そこから 16 秒ごとにレートが下がる。1回目は「レート × 0.75」の切り捨て、2回目以降は「1つ前のレート ÷ 2」の切り捨て（下がり方は原作の擬似コードに合わせる）。14 回目かレート 1 で止まる。レート 70 なら 70 → 52 → 35 → 26 → 17 → 13 → 8 → 6 → 4 → 3 → 2 → 1。

### 4.8 配ぷよ（eスポ互換）
- 乱数: `seed = seed × 0x5D588B65 + 0x269EC3`（32bit）。値は `seed >> 16`、`n` 未満の値は `(r × n) >> 16`
- 初期シードは 16bit（65536 通り）
- 手順: 5色の割り当てを決める → 3色・4色・5色のプールを各 256 個作ってシャッフル → 4色・5色プールの先頭4個を3色プールの先頭4個で上書き（最初の2手は3色以内）
- 256 個 = 128 手でループ
- Puyo Nexus に載っている参照実装と、公開されている配ぷよデータの先頭数手が一致することをテストで確かめる

### 4.9 試合
- 2〜4人。最後まで残った1人が勝ち。同じフレームに全員負けたら引き分け
- 先取数は部屋ごとに設定（初期値: 2本先取）。原作大会の「2本先取を2セット」もオプションで選べる
- 4人のとき、攻撃は1人に向かう（ターゲット方式）。決め方はフィーバー・レイアウトの追加調査の結果で確定する。それまでの仮の仕様は「いま予告の一番少ない相手、同じなら盤面が一番低い相手」

## 5. フィーバールール

サブプロジェクト③で詳しく決める。追加調査（フィーバーゲージ、フィーバー盤面の連鎖のタネ、ツモの形と回転、得点・レート）の結果をここに追記する。①②のエンジンは、ツモの形（2個・3個・4個・でかぷよ）とルール差分（`rules/*.ts`）を差し替えられる作りにしておく。

## 6. 見た目

### 6.1 ぷよ
- 画像ファイルは使わず、PixiJS の Graphics とシェーダーで描く
- 形: 丸いゼリー。上に白いハイライト（ツヤ）、下にうっすら影と濃い縁
- つながり: 上下左右の同じ色とつながると、間が溶けて伸びた形になる（連結した方向をビットで持って、16 パターンを描き分ける）
- 顔: オリジナルのシンプルな目。原作の目のデザインはまねしない
- 色: 赤・緑・青・黄・紫・おじゃま（半透明の白）。設定で色ごとのマーク（●▲■など）を出せる

### 6.2 動き
| 場面 | 演出 |
|---|---|
| 設置 | 縦につぶれて横に広がり、ぷるんと戻る（約 8F） |
| ちぎり・連鎖後の落下 | 着地でバウンド。上のぷよほど揺れが遅れて伝わる |
| 消える前 | 点滅してからはじけて、粒が飛ぶ |
| 連鎖 | 消えた位置に「n連鎖」を表示。連鎖数が大きいほど大きく派手に |
| おじゃま | 落下・着地で、量に応じて画面を揺らす |
| 全消し・負け | 全消しの表示。負けたら盤面が崩れて落ちる |

演出はエンジンのイベント（`events.ts`）を見て描画側だけで行う。エンジンのフレーム数には影響させない（ゲームのテンポは §4.4 の値で決まる）。

### 6.3 レイアウト
- 基準解像度は 1920×1080。ウィンドウに合わせて全体を拡大縮小する
- 2人: フィールドを左右に置き、NEXT/NEXT2・スコアを内側に、予告ぷよを各フィールドの上に出す
- 3〜4人: フィールドを横に並べて縮小し、攻撃先をマーカーで出す
- 通とフィーバーで背景と枠のデザインを変える（通: 落ち着いた色、フィーバー: にぎやかな色）
- 具体的な比率と配置は、追加調査（原作の画面レイアウト）の結果を反映する

### 6.4 音
効果音は Web Audio で生成する（設置、回転、移動、連鎖音（連鎖数で音が上がる）、おじゃま、全消し、負け）。BGM はなし（あとでフリー素材を足せる）。

## 7. CPU

- **考え方**: 置ける場所（最大 22 通り × 回転）を全部試して、そのあとの盤面を評価する。NEXT・NEXT2 まで見る、ビームサーチ（有望な候補だけ残して先を読む探索）
- **評価**: 「いま撃てる連鎖の大きさ」「1個足したら起こせる連鎖の大きさ（ぷよを仮に落として試す）」「盤面の形（谷・高さのバランス）」「13段目・窒息点の危険度」。前作の `src/games/puyo/ai.ts` の評価関数を参考にし、`ama`（eスポ向けのオープンソース AI）の考え方を取り入れる
- **発火の判断**: 予告の量と相手の盤面を見て、大連鎖を撃つか、小さい連鎖で返すかを決める
- **操作**: 決めた置き場所まで、人と同じ入力（移動・回転・ソフトドロップ）で動かす。エンジンのルールをそのまま通るのでズルにならない
- **強さ（5段階）**: 先読みの深さ、ビーム幅、操作の速さ（1手あたりの待ちフレーム）、たまに2番目の候補を選ぶ確率で調整する
- **実行場所**: Web Worker（メインスレッドを止めないため）。1手の思考は 1 フレーム（約 16ms）以内を目標にし、間に合わなければ前の候補を使う

## 8. オンライン

### 8.1 方針
各プレイヤーは**自分の盤面だけを自分の PC で動かす**。送るのは出来事だけ。相手の盤面は届いた出来事を自分のエンジンで再生して表示する（同じシードと決定的なエンジンなので、置き場所が分かれば盤面が再現できる）。

### 8.2 部屋
- 6文字の部屋コード。最大4人。ホストがルール（通/フィーバー）・先取数・レートを決める
- 全員が「準備OK」でホストが開始。ホストがシードとサーバー時刻での開始時刻を書き込み、全員がその時刻にカウントダウンを終える
- Firebase のパスは前作とぶつからないように `puyoRooms/` の下に置く。セキュリティルールは前作の `rooms` の形を参考に追加する（Firebase コンソールでの公開はユーザーが手で行う）

### 8.3 送る出来事
| 出来事 | 中身 |
|---|---|
| 設置 | ラウンド番号、手数、列・向き、自分のゲームフレーム |
| 攻撃 | 送ったおじゃま数（相殺後）、攻撃先、フレーム |
| おじゃま落下 | 降った数と列（受け手が決めて送る。相手画面の再生に使う） |
| 負け | フレーム |

- 攻撃は受け手が「届いた時点」で予告に積む。受け手の画面での相殺と落下は受け手が判断する（自分の盤面のことは自分が正しい）
- そのため、ラグがあると各自の画面で予告のタイミングが少しずれることがある。オンライン対戦ではこれを許容する（原作のオンライン対戦も同じ考え方）

### 8.4 切断
- 切断を検知したら（Firebase の onDisconnect）、その人をそのラウンドの負けにする
- 10 秒以上なにも届かない相手も負けとして扱う

## 9. エラー処理
- Firebase につながらない: オンラインのボタンを無効にして理由を表示。ひとり練習と CPU 対戦は普通に遊べる
- 部屋がない・満員・始まっている: ロビーでメッセージを出す
- 描画が WebGL に対応していない: PixiJS の Canvas フォールバックは使わず、「対応していないブラウザです」と表示
- エンジン内部で矛盾が出たとき（開発中のバグ）: 開発ビルドでは例外で止め、本番ではそのラウンドを終わらせて結果画面へ

## 10. テスト
- **エンジン**: 実測フレーム表（設置・連鎖・ちぎり・おじゃま落下）をそのままテストケースにする。得点表、相殺、端数の持ち越し、マージンタイムのレート表、全消し
- **配ぷよ**: 参照実装と公開データとの一致
- **決定性**: 同じシードと同じ入力列で2回動かし、全フレームの状態が一致する
- **CPU**: どの強さでも窒息せずに一定時間積める。1手の思考時間の中央値が基準以内
- **オンライン**: `MemoryTransport` で2〜4人の部屋を作り、開始・攻撃・切断・勝敗を確かめる
- **見た目**: 自動テストはしない。サブプロジェクトごとにブラウザで動かし、スクリーンショットで確認する
